# 健康资讯更新实施计划

状态：2026-10-04，更新功能规划阶段；未接真实来源、未启用采集。独立 `/portal` 页面已由 DSH 实现（见 `COORDINATION.md` 的 `4283427` 报告），本文件专门定义新闻如何更新。沿用 `NEWS_PORTAL_IMPLEMENTATION.md` 的页面与空状态契约。根目录 `NEWS_FEED_PLAN.md` 中“复用医学知识 prototype 通道”的设想在此修正：新闻采用**独立资讯表和读取接口**，不进入 `knowledge_*`、向量库或咨询检索。

## 1. 目标与明确边界

- 目标是展示可核对的全球医疗卫生资讯和养生、健身、疾病、药物四分类内容；用户已确认**每天最多自动更新一轮**，不承诺每个来源每天都有新闻，也不称为实时推送。
- 只展示原题、来源、原文 HTTPS 链接、发布时间、获取时间和简短自编摘要；不镜像全文，不把抓取时间冒充发布时间。摘要无法可靠生成时可只显示标题、来源和链接。
- 每条新闻标注“资讯，未经医学审核”；不能自动成为正式医学知识，也不能直接作为诊断、用药或治疗建议。小贴士与新闻分开治理，不能把新闻自动改写为养生/健身建议。
- 不按健康记录、病史或咨询内容个性化推荐。不在用户电脑注册计划任务、Windows 服务或开机自启。

## 2. 推荐更新机制

采用**每日首次访问触发 + 最近成功快照 + 显式前台 CLI**，不是让每个浏览器请求直接抓外网。每日窗口按 `Asia/Shanghai` 的 04:00 至次日 03:59:59 划分；这是产品更新日，不是“距离上次成功恰好 24 小时”。

1. `/portal` 请求 `GET /api/v1/news?category=...`；API 只读数据库中的最近成功快照，立即返回条目、`asOf`、来源级状态和 `nextRefreshAt`。没有缓存时返回 `sources_not_connected` 或 `empty`，不伪造内容。
2. 当天首次访问且存在已配置、已准入来源时，服务端尝试触发**同一应用生命周期内**的一轮有界刷新。持久化 `update_day` 与租约，保证重启和多用户/多进程并发时每日最多一轮自动刷新；一次刷新逐个处理已启用来源。接口不等待外网抓取完成，服务停止则刷新停止。
3. 刷新器按来源适配器读取 RSS/Atom、官方 API 或已核准的栏目页；遵守该站许可、robots 和速率限制。逐条校验 URL、来源、标题和时间，规范化链接并去重；写入新快照与来源结果。
4. 刷新失败时保留最近成功内容但标为 `stale`，显示最后成功时间与失败来源数量；超过展示有效期则隐藏过期条目，不把旧新闻标为“今日”。同一天不自动无限重试；用户 2026-10-05 追加确认：自动轮失败或部分失败后，允许全站一次受限的用户后台重试（`POST /api/v1/news/refresh`），成功轮不允许重试。显式 CLI 仍允许运营人员在前台手动刷新和查看结果；同日 CLI 手动轮会占用用户重试额度。
5. 当天无人访问就不运行、不补跑；下一次访问触发当日的一轮。若将来确需无人访问时准点更新，应在正式部署环境中另行批准由项目生命周期管理的任务进程；本机不落持久化自启动。

推荐初始参数（上线前以来源许可和实测调整）：每天 04:00 切换更新日、单次每源最多 20 条、单源请求超时 8 秒、轮内有限重试、列表展示最近 7 天；参数必须配置化。先做 1–2 个可合法自动读取的来源验证，再扩充。

## 3. 数据与接口

- 独立 `news_sources`：来源 ID、名称、主页/订阅地址、分类范围、抓取方式、许可核验记录、启用状态、最后尝试/成功时间、最近错误码。
- 独立 `news_refresh_runs`：`update_day`（北京时间日期，自动运行唯一）、状态、触发方式、开始/完成时间、租约到期时间与来源级成功/失败计数。手动运行另行记录，不能抢占正在运行的自动任务。
- 独立 `news_items`：稳定 ID、来源 ID、分类、原题、自编摘要、规范化原文 URL、原文发布时间（可空）、首次/最近获取时间、展示到期时间、指纹、`medical_reviewed=false`。URL 与来源 ID 联合去重，标题指纹处理同文多 URL；来源撤回后立即停止展示。
- 不在前端返回原始异常、页面 HTML 或抓取日志。来源状态使用受控码，例如 `ready`、`partial`、`stale`、`empty`、`failed`；现有 `sources_not_connected` 保留。`asOf` 指最近成功快照时间，而非接口调用时间。
- `GET /api/v1/news` 保持需登录、按分类读取，增加分页和来源状态字段时先版本化契约与测试。手动刷新仅提供运维 CLI；不开放普通用户触发全站抓取的 API。
- 来源配置不能直接把现有医学知识注册表 `approved_for_ingestion` 当作新闻采集授权。两套用途分开审核；现有 `automated_collection_enabled=false` 是硬边界，在具体来源的许可、法律和医学审查完成前不翻转。

## 4. 实施顺序与验收

| 阶段 | Codex 后端 | DSH 前端 | 验收 |
| --- | --- | --- | --- |
| N0 来源准入 | 为候选来源逐站核对 RSS/API、许可、robots、更新频率与分类；得到用户对首次自动采集来源的确认 | 独立 `/portal` F1 框架完工 | 未核准来源不得抓取；无假新闻 |
| N1 离线数据层 | 建独立表、迁移、来源适配器接口、校验/去重/失效测试；用固定本地样例，不联网 | 按冻结契约做 `ready/empty/partial/stale/failed` 桩测试 | 禁 SSRF、重复、过期、撤回；资讯不进入 RAG |
| N2 单源真实试跑 | 对 1 个已准入来源做前台 CLI 小批量试跑，记录原文链接、时间与失败原因 | 列表显示来源、两种时间、未审核标记 | 人工逐条核对真实条目；不复制全文 |
| N3 每日按需更新 | 增加北京时间 04:00 更新日、数据库唯一约束与租约、超时/轮内重试、来源级状态与监控；逐站扩源 | 处理刷新中、部分失败和过期提示；1280/375 浏览器验收 | 同一更新日并发/重启后最多一轮自动刷新；无人访问不运行；来源失败不清空最近成功数据；本机无自启动 |

## 5. 开始 N0 前必须确认

用户需决定第一批是否**只接经逐站核验可自动读取的官方/专业机构来源**。推荐如此开始；这不是把用户的普通联网问答搜索范围缩回三站，而是独立资讯产品的来源准入。商业新闻 API、自媒体与全网爬取不在首批范围。N0 涉及外网检查，执行前按项目规则另行征得联网许可。
