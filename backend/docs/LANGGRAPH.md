# LangGraph 咨询工作流

## 当前范围

当前使用两张职责分离的图。用户消息保存时运行轻量安全图，只做确定性红旗预检；
用户点击生成时运行生成上下文图，先复检红旗，再执行医学 RAG 检索，最后允许流式
模型调用。这样不会在保存消息的数据库锁事务中等待云端向量服务。

~~~mermaid
flowchart LR
    START --> triage[确定性红旗预检]
    triage -->|emergency| emergency[停止 AI 生成]
    triage -->|continue| gate[医学相关性门控]
    gate -->|医学问题| retrieve[查询脱敏与 pgvector 检索]
    gate -->|普通聊天| ready
    retrieve -->|证据不足且开发环境命中受控主题| web[受限官网搜索]
    retrieve --> ready[生成就绪]
    web --> ready
    emergency --> END
    ready --> END
~~~

- triage：调用 app.safety.evaluate_triage，不依赖大模型。
- emergency：输出 emergency_end，现有接口随后展示固定紧急分流卡并阻止模型调用。
- retrieve：最多召回 4 个当前 embedding 配置对应的证据块；生产环境只允许 approved，
  开发环境还允许 prototype。受控向量服务错误会标记 failed 并降级为空证据。
- retrieval_gate：使用本地确定性规则识别症状描述、疾病、用药、检查、预防和就医
  问题；问候、模型身份、产品操作、写作和普通闲聊跳过检索，不产生向量调用费用。
- generation_ready：把检索状态和证据交给流式接口，再作为隔离系统上下文传给用户
  选择的模型。
- web_search：仅在开发环境、受控主题且本地证据为空或覆盖不足时搜索允许的官方
  站点；搜索摘要标记为 prototype，不能自动升级为已医学审核资料。

红旗路线严格位于门控和检索之前，命中时不会调用向量模型或聊天模型。普通聊天的
`retrieval_status=skipped`，但仍允许聊天模型正常回答；医学路线的状态为 completed、
empty 或 failed。任何情况下都不能伪造来源。

门控不调用大模型，结果可预测且成本低，但关键词规则不可能覆盖所有自然语言表达。
新出现的漏判和误判应先加入门控测试集，再扩充规则；不得把门控结果解释为医学分类。

## 状态与隐私

图使用独立的输入、内部和输出状态：

- 输入状态包含本次 user_text，只供预检节点使用。
- 输出状态只返回路线、规则版本、规则 ID、分流结果和下一步。
- 原始症状文本不会出现在图输出中。
- 数据库会话只在内存中作为检索节点依赖传入，也不会出现在图输出中。
- 当前不配置 checkpointer，也不启用外部追踪，因此 LangGraph 不会额外持久化健康文本。
- 用户消息仍按现有机制加密保存在 PostgreSQL 中。

## 后续扩展顺序

生成上下文图已完成 RAG 接入，后续按以下顺序演进：

1. 判断是否需要结构化追问。
2. 将用户补充信息标准化为检索条件。
3. 对召回结果增加关键词混合检索和重排序。
4. 已在流式路由做来源编号核验；下一步增加在输出对用户可见前生效的安全检查，
   再用独立评测题集核对逐句医学陈述是否得到对应资料支持。
5. 扩充前端可恢复的检索状态及无证据提示（当前已提供部分即时提示）。

流式模型传输和消息持久化仍由 FastAPI 路由负责；LangGraph 当前负责编排红旗复检、
RAG 与生成准入。红旗预检结果继续加密写入消息记录，流式接口还会检查已保存结果，
形成第二道安全拦截。

模型产生实际科普正文后，流式路由通过 `app/rag/citation_audit.py` 按本轮证据
片段编号核验正文中的 `[来源N]`，只加密保存实际标注且编号存在的引用；同一 URL
下多个片段保留原编号。无效编号不作为可核验来源展示。前端折叠区域中，旧版
消息的未核验检索候选明确标注为历史资料；结构化追问不展示来源，prototype
不提供无效外链。编号匹配不代表医学陈述被证据支持；流式中间文本尚未经过
生成后的引用核验。
